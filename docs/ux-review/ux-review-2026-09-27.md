# CRM Web Checklist UX Review

Overall state: the app has a strong operational foundation and several thoughtful safeguards, but the main work surfaces still behave like desktop tables on narrow screens, and the admin dashboard/settings flows hide too much meaning behind icons and dense checkbox grids.

## Screen Inventory

- `/admin/login`: email/password admin login plus Google sign-in.
- `/admin`: admin dashboard listing all client checklists, progress, links, exports, settings, duplication, token regeneration, and delete.
- `/admin/new`: checklist creation flow, sampled by code structure only.
- `/admin/checklists/[id]/welcome`: checklist overview, progress summary, module rail, save/export/snapshot actions.
- `/admin/checklists/[id]/[tab]`: repeated checklist data-entry tabs, sampled with Pre-Screening Questions.
- `/client/[slug]` and `/client/[slug]/[tab]`: client-facing checklist shell, reviewed by shared layout/code; live route not fully exercised to avoid editing client data.
- `/editor/[token]` and `/editor/[token]/[tab]`: editor-token checklist shell, reviewed by shared layout/code; live token flow not fully exercised.
- `/admin/[slug]/configurator`: configurator checklist generated from CRM settings, sampled with EXL.
- `/admin/checklists/[id]/snapshots`: snapshots route identified, not deeply exercised.

Core flows reviewed:

- Admin signs in and scans checklist status.
- Admin opens a checklist and moves through modules.
- Admin fills/reviews a spreadsheet-style tab.
- Admin configures a checklist's channels/tabs.
- Admin reviews configurator steps and exports them.

Mixpanel was checked read-only. Accessible projects were `Goodgets Data`, `UAT Tool`, `Journo`, `Nutrilog Data`, `Healthsage iOS`, and `Jolo`; none clearly matched CRM Web Checklist. No CRM-specific usage sample was available, so priority is based on core-task importance plus visual/code evidence.

Where to start without usage data:

1. Checklist data-entry tabs, because they are the core client/admin completion workflow.
2. Admin dashboard, because it is the routing hub for every checklist.
3. Checklist shell/navigation, because it repeats across admin, client, and editor views.
4. Settings dialog, because it controls client-visible scope and notification behavior.
5. Configurator checklist, because it translates client settings into Talkpush admin steps.

## Top 5 Quick Wins

1. Row #7: collapse mobile checklist header actions into a More menu.
2. Row #4: replace the dashboard's eight visible icons with one primary action plus a More menu.
3. Row #3: allow two-line module labels on desktop so names do not truncate immediately.
4. Row #6: wrap configurator action text on desktop, even before the full mobile card redesign.
5. Row #5: add a plain summary line to settings: "Client-visible tabs: N" and "Owner notifications: on/off".

## Bigger Redesign Ideas

1. Mobile checklist row cards: keep desktop spreadsheet power, but render phone/tablet rows as labeled cards with required fields, completion status, and row actions. Trade-off: more component work, but it fixes the largest completion risk.
2. Dashboard action model: change from icon toolbar to primary action + menu. Trade-off: one extra click for rare actions, but much lower accidental-action risk.
3. Settings wizard-lite: split owner notifications, communication channels, and client-visible tabs into sections with a review summary. Trade-off: slightly longer setup path, but much clearer consequences.

No mockup file was created in Phase 1 because the existing screenshots make the layout problems direct enough to implement from the recommendations; before/after screenshots should be added during Phase 2 if rows are selected.

## What's Already Good

- The app has meaningful autosave/save/discard language and visible progress.
- Destructive delete and editor-link regeneration use confirmation dialogs.
- Spreadsheet mode has useful power-user features: paste support, column width persistence, sticky leading columns, and required-field attention banners.
- Configurator progress is clear at the top of the page.
- Icon buttons generally have accessible names, even when visual labels are missing.
